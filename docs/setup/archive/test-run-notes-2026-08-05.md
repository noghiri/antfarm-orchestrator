## For assessment (larger architectural questions, not simple to-dos)

- **Rewrite orchestrator as a compiled Rust tool, cross-platform (Windows/Linux), with a TUI that runs the Claude sessions inside embedded terminal-emulator panes and monitors staging/status.** Currently the orchestrator is a PowerShell script (`orchestrate.ps1`) spawning separate `claude` processes per stage with state tracked via a JSON file on disk — this would replace that with a single compiled binary owning process lifecycle, an embedded terminal emulator per running `claude` session, and a TUI for at-a-glance status across stages/features (could also address item 10's "what's actually running" visibility gap). Needs a real feasibility/effort assessment before treating as a to-do: scope of `orchestrate.ps1`'s current responsibilities to port, Rust crates for embedded terminal emulation + cross-platform PTY handling, and whether the complexity is justified versus incremental fixes to the current script.
    - **Potential added benefit:** a TUI with multiple terminal panes could also enable a better, tab-based method for handling escalations (e.g. a dedicated tab per paused/escalated feature the human can switch to directly), versus the current copy-paste-a-message-between-sessions flow (see archived notes item 18's escalation hand-off friction).
    - **Potential added benefit:** a long-lived owning process could also keep the orchestrator "alive-ish" across the whole run (rather than being fully torn down and re-derived from disk state at every stage boundary), which could help with routing/continuity issues like item 10 and the escalation hand-off gap above — though this cuts against the current per-stage clean-process-boundary design (archived notes item 4/7), so the tradeoff needs to be weighed explicitly as part of the assessment, not assumed to be a free win.

- **Reconcile the split between GitHub Issues and on-disk state files as sources of truth** — state is currently spread across both GitHub (issues/labels, per `github-ops:*` skills) and local on-disk state files (`state.json` etc.), and it's unclear how to best clean this up into a coherent single model. Open question, not yet a scoped to-do — needs its own design pass to decide what belongs where (or whether to consolidate onto one), and may interact with the Rust/TUI rearchitecture and multiplayer ideas above (e.g. `workflow-utils:reconcile-state` already exists specifically to paper over this split on startup, which is itself a symptom).

- **Explore making the orchestrator "multiplayer"-capable** — i.e. multiple humans collaborating on/observing the same orchestrator run (not to be confused with `workflow-utils:multi-instance`, which is about multiple *orchestrator instances* coordinating claims on the same project). Raised alongside the Rust/TUI idea above, as a similarly large architectural question rather than a scoped to-do — needs its own feasibility/design assessment (e.g. what "multiplayer" concretely means here: shared visibility, concurrent decision-making, role separation between participants) before it's actionable.
    - **Proposed shape:** a multiplayer form of this would probably look like a series of "meetings" with both humans and agent ("robot") participants involved, rather than each human having an isolated 1:1 session with the orchestrator — e.g. stage-gate reviews or escalation resolution as a shared, multi-party session rather than a private exchange.
